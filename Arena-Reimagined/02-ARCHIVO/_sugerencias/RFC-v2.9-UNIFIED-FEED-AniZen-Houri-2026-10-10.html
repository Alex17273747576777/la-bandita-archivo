    §0 · Abstract

    The Feed becomes an object

    This proposal turns the newly shipped multiFeed of AniZen and Houri into what it was originally requested to be: multiple feeds — a global feed by default, segmentable by hand or by on-device AI, each feed carrying up to 20 sources bound the worst-case refresh by construction (per-source page budget × ≤20); budgets are device-tier config and are measured in QA fixtures — the spec makes no wall-clock promises.

    §0 · Status of this document — the ladder and its criteria A status label without a criterion is a claim, not a status. An earlier version of this document said «Production Candidate» about a proposal with no merged code — over-claimed, demoted here (P1 applies to this document too). Draft for review ← this document (declared by the author) → Reviewed (each maintainer states the spec is implementable, or lists what blocks it) → Accepted, per repo (a maintainer commits — milestone or issue state) → Production Candidate, per repo (a merged implementation behind a feature flag passes every §8 acceptance criterion in that repo’s CI: golden-file rules parity, airplane-mode, feeds.json round-trip, ≤20-source budget fixtures — declared by the repo’s maintainer, never by the proposal author) → Shipped (enabled by default in a stable release).
    I Feed = portable object

    Not a screen: a versioned feeds.json (feed.v2.3) that lives on the Universal Source Manager, travels inside .anizenbk / .hourbk backups, survives device moves and repo shutdowns.

    II Filters = declared capability

    Each adapter declares a FilterProfile; the UI renders exactly what the selected source can do — native chips, honest «local filter» fallbacks, never a fake.

    III Segmentation = rules first, AI second

    Deterministic rules (plain data, portable, testable) cover the 90% case; AI is opt-in, on-device, per-entry correctable — the airplane-mode test decides.

    Reading map — three live exhibits §4 runs the per-source chip re-binding that fixes the reported gap; §5 simulates the three merge policies with a real duplicate; §6 executes the manual rule engine on sample entries. All three are deterministic, zero-network, and live inside this single file.

    Resumen ejecutivo

    Para los equipos, en español ES

    Este documento eleva a nivel de arquitectura dos observaciones enviadas por el dueño de esta propuesta al equipo de AniZen y Houri tras la reciente implementación del nuevo tipo de Feed:

    1. El MultiFeed actual muestra una sola fuente y no expone filtros. Al seleccionar una fuente concreta dentro del multifeed debería poder alternarse entre sus filtros específicos («recientes», «actualizados») y los convencionales («nuevas obras», «populares», «en tendencia»).
    2. La petición original era un multifeed de verdad: múltiples feeds. El feed global por defecto, más la capacidad de segmentarlo en categorías — a mano o mediante IA que clasifique automáticamente las entradas existentes. Ejemplo real del ecosistema: fuentes de películas y fuentes de anime conviven hoy en las mismas apps (Zangetsu, AniDash, Mangayomi); cada feed, igual que el global, debería admitir hasta 20 fuentes o extensiones.

    En la v2.1, tras la primera revisión del mantenedor, se añaden compromisos explícitos: la fila de filtros se genera de lo que cada fuente realmente admite con una escalera de retroceso declarada por fuente (§4.1); la clasificación IA se ejecuta una vez por trabajo y se cachea la etiqueta — jamás en el camino del render (§6.3); la anulación manual es permanente y visible; la identidad del trabajo es canónica y declarada por feed (§5.1); y una fuente caída o eliminada no detiene ni reordena el feed (§5.2). La v2.2 absorbe la segunda ronda: suelo cronológico y aliases declarados en la escalera (§4.1), histéresis y GC de etiquetas (§6.3), pines por work_key con granularidad, desempate canónico determinista con badge de lectura (§5.1), superficie de degradación y refresh incremental (§5.2), y dos almacenes con un camino de escritura cada uno (§6.4). La v2.3 responde la pregunta que decide el progreso: los cinco mecanismos de v2.1 sobreviven y ahora cuelgan de tres principios estructurales con tabla de trazabilidad (§2.1), más siete endurecimientos: precedencia total con pozo «Sin asignar» y rules_packs versionados (§6.1), prueba de arranque en frío (§6.3), higiene del objeto portable sin credenciales jamás (§7), fuente faltante visible (§5.2), fallback local recomputado jamás cacheado (§4.1) y el ≤20 como presupuesto de latencia declarado (§2.2).

    Tesis de esta v2 El Feed no es una pantalla — es un objeto portátil de primera clase, que vive sobre el Universal Source Manager del RFC v1, viaja dentro de los backups autocontenidos (.anizenbk / .hourbk), y expone los filtros nativos de cada fuente mediante una interfaz normalizada. La evidencia del ecosistema (§1) muestra que la segmentación por categorías es la regla del mercado; el feed único global es la excepción.

    §2 · Goals

    Design goals

    01 Feed as a first-class, portable object

    Created, named, edited, backed up, restored.

    02 Respect native source capabilities

    The filter row is generated from what each source actually supports, with a declared fallback ladder — never an empty chip, never a silent bucket (§4.1).

    03 Manual first, AI second

    Deterministic rules cover 90% of needs; AI is a suggestion layer over hand-made structure — opt-in, on-device, correctable, cheap at runtime.

    04 Zero telemetry

    Classification runs on-device; nothing about a user's taste leaves the phone.

    05 ≤20 sources per feed

    As originally requested — any adapter mix (APK manga, APK anime, Kotatsu DEX). A declared latency budget, not a UI taste (§2.2).

    06 Global feed remains the default

    Segmentation adds; it never removes.

    07 Classify once, render forever

    No AI work in feed render or scroll paths — label cache only (§6.3).

    08 Degradation must be boring

    A dead or removed source never blocks, re-sorts, or re-identifies a feed (§5.2).

    09 Source neutrality (v2.4)

    The app bundles no sources and no content: feeds present entries only from sources the user already installed; catalogs are cited as market evidence, never as content.

    2.1 — Three structural principles & the mechanism map v2.3

    The mechanisms of v2.1/v2.2 are not a bag: they hang from three principles. Every future feature must state which principle carries it — if none does, it does not ship.

    P1 Honest capability

    Render what each source can actually do; degrade visibly. A silent feed is a defect, not a state.

    P2 Deterministic, data-first segmentation

    Rules, identities and precedence are declared data — same inputs, same segments, on every device, cold or warm.

    P3 Derived vs intent

    Disposable compute and durable intent live in separate stores with separate write paths; the portable object carries intent, references capabilities, never secrets.

    2.2 — Why 20 sources: a latency budget v2.3

    The ≤20 cap is a budget line, inherited from the owner's request and now declared: per refresh, merge cost ≈ Σ(one page per source) + interleave — 20 sources bound the worst-case refresh to a few seconds and bound memory on low-end devices. The UI limit is the consequence, not the cause. Device tiers may lower the number; nothing raises it silently.

    Fallback rule — no fake filters If a source lacks a native endpoint for a requested filter, the engine (a) hides the chip, or (b) offers client-side post-filtering over already-fetched pages, visibly labeled «filtro local — no nativo de la fuente». Never silent.

    4.1 — Fallback ladder: declared per source, never improvised v2.1

    “Popular” and “trending” are not universal concepts. When a source does not expose a bucket, the engine walks the ladder declared by that source in its FilterProfile — it never renders an empty chip and never silently dumps everything into one bucket:

    1. Native — the source exposes the bucket's own endpoint → chip rendered as native.
    2. Declared alias — the profile's versioned alias map maps another of the source's endpoints to the bucket ("aliases": { "trending": "popular" }) → rendered as native, tooltip names the backing endpoint. Nothing is inferred at runtime: if the map does not declare it, the alias does not exist — no guessing game one level down.
    3. Local post-filter — client-side filtering over already-fetched pages → chip visibly labeled «filtro local — no nativo de la fuente».
    4. Chronological floor (v2.2) — every adapter family exposes latest/updated, so a source that matches no bucket above still serves it chronological and labeled as such («cronológico — la fuente no expone popular»). The rung is never silent, and the feed is never indistinguishable from empty.
    5. Hidden — visible, never silent (v2.2) — only a source with no working listing at all ends hidden, and that state is visible per source in the feed's health row («esta fuente no expone filtros» / «sin respuesta»). A source can no longer contribute nothing without signal.
    Self-describing sources The ladder lives in the source's FilterProfile — part of its manifest, alongside extension metadata. Adding a source is self-describing: the feed UI learns what the source can do without new feed-side code. Ladder order is per-source data, reviewable in QA fixtures, versioned with the source.
    Local-fallback honesty constraint — v2.3 A local filter can only trim the already-fetched window — its result is a function of window size and fetch order, and both are declared by the adapter in the FilterProfile. Local results are recomputed on every refresh and never cached: the window moves underneath them, and an honest fallback that goes stale is just a slower lie.

    • Source chips (one per enabled source of the feed, max 20) + filter chips row that re-binds to the selected source's FilterProfile (§4) — this is the exact gap reported.
    • Feed switcher: horizontal tabs — Global · user feeds · «+ New feed». Long-press → rename, reorder, export single feed.
    • Merge policies (per feed): interleave (round-robin, default), weighted (per-source weight), recency (strict time order across sources; ties → source id, in-source order — fetch-order independent, v2.5). Deduplication by normalized entry key (title-cased ASCII-fold + source id) with «show duplicates» toggle.
    • Per-source state inside the feed (solo mute, weight, filter override) — so «this source, its filters» is one tap, not a detour to the Sources screen.

    5.1 — Canonical work identity & duplicates v2.1

    The global feed will surface the same work from multiple sources. The behavior is declared data, per feed, not an accident:

    • work_key = normalized title — NFKD, strip combining marks (\p{M}), casefold, fold to ASCII (Turkish İ must equal i, v2.5) + content type + declared creator/year when exposed. Hashed locally; nothing leaves the device.
    • policy: "canonical" (default for Global): duplicates collapse to the first occurrence; a badge lists the others («también en B, C»). No silent merging of chapter/episode state across sources.
    • Canonical tiebreak is deterministic (v2.2): (1) the feed's primary source if the user pinned one, (2) richer metadata (count of non-null fields), (3) most recently updated entry, (4) stable lexical order by source id. Same winner every session — collapse is never non-deterministic.
    • The badge tells the reading truth (v2.2): «canónica en A»; if the user's download came from B, «leyendo desde B · canónica en A», with a one-tap «usar B como canónica» — a primary-source pin that feeds tiebreak rule (1).
    • Collision-conservative by default (v2.4): same title ≠ same work (Fruits Basket 2001/2019). Collapse requires exact full-key equality; yearless keys only merge with yearless or equal-year keys; residual ambiguity never auto-collapses — it shows a visible «posible duplicado» badge. When in doubt, keep duplicates: P1 forbids faking a merge.
    • Badge inventory (v2.4, closed set): «también en B, C» · «leyendo desde B · canónica en A» · «posible duplicado» · stale-with-label («sin actualizar desde…») · «fuente faltante» · «Sin asignar» · pin mark. New badges require a spec row — no UI drift.
    • policy: "keep_duplicates" (per feed; sane for library-adjacent feeds): duplicates stay visible; the filter-by-source chips (§4) are how users separate them.
    • The «show duplicates» toggle overrides either policy temporarily, per session.

    5.2 — Stable feed identity under removal or outage v2.1

    Multi-source feeds degrade badly when a source dies. Rules, in order of importance:

    • A downed source never blocks the feed. Merge is partial-success: live sources refresh; the downed one serves its last cache stale-with-label («sin actualizar desde el 8-oct») instead of stalling or vanishing.
    • No global re-sorting on failure. Entry order for surviving sources is untouched; the failed source's block keeps its position, flagged. A flaky source must not make the feed feel haunted.
    • Degradation has a specified surface (v2.2): a feed-level banner («2 fuentes sin actualizar · última sincronización 8-oct») and per-item markers on entries served stale — the banner is feed state, the markers are attribution.
    • Degraded refresh is retry-failed-only (v2.2): live sources serve from cache and are not re-fetched; only the failed sources retry, merged incrementally. A full re-fetch exists only as an explicit user action. Documented as the rule, not as an optimization.
    • A missing source is a visible state, never a silent loss (v2.3): if a referenced source id is absent on restore or import (renamed, removed, not yet installed), the feed loads with a «fuente faltante» placeholder block in the switcher and health row — the feed says so, always.
    • Removal is identity-preserving. Deleting or disabling a source changes nothing else: the feed keeps its id, name, order, rules, and pins. feed_global is immutable and non-deletable by definition.
    • Health is visible where it matters (RFC v1 §5): per-source row inside the feed shows last-success timestamp and state — not a global error toast.

      §6 · Segmentation

      Manual first, AI assisted, always correctable

      6.1 — Manual rules (deterministic, portable, testable)

      source_in · content_type (manga/anime/novel/movie) · genre/tag in · title contains · status in — combined with AND/OR. Rules are data — no code, no lock-in.

      Precedence is total, not emergent (v2.3): every rule carries an explicit priority (integer, lower wins); evaluation sorts by (priority, declaration order) — a total order — and the first matching rule takes the entry. An entry matching no rule goes to the visible «Sin asignar» pool — never dropped, never auto-spread; the pool is a real segment in the feed UI and its size is part of the QA fixture output. Same rules + same entries ⇒ same assignment on any device, warm or cold; golden-file tests pin this.

      Rules are independently versioned (v2.3): the rule set lives in its own addressed object (rules_packs with rules_version), referenced by the feed — rule tweaks bump rules_version and migrate on their own; the feed schema (feed.v2.3) moves only when the feed object itself changes shape. One data change must not burn the schema's migration budget. The pack reference is content-addressed (v2.4): it carries the sha256 prefix of the rules array, and restore verifies it — an id/version/content mismatch fails loudly with a report — honestly stated: this guards drift and mismatch, not malice (v2.5). The «Sin asignar» pool is the single visible bucket across producers (v2.4): an entry lands there either when no rule matches (rules producer) or when no cached label exists yet (AI producer) — one pool, two feeds into it. Render caps the pool view with a count summary («+112 más»); the data stays whole (v2.5).

          6.2 — AI-assisted segmentation (opt-in, on-device, correctable)

          • Input: the existing entries of the Global feed (titles, genres, tags, content type metadata).
          • Engine: small on-device classifier; AniZen can ship it on its existing AI diagnostics stack (RFC v1 §5); Houri ships the lighter tier (rules + heuristics) first.
          • Behavior: proposes suggested feeds (e.g., «Anime», «Movies», «Donghua», «Long-runners») with per-entry confidence; the user accepts, edits, or discards each suggestion. AI never moves an entry silently — every assignment is reviewable, reversible, and locally computed.
          • Privacy (precise invariant, v2.4): nothing user-derived ever leaves the device; the segmentation pipeline makes zero network calls; model binaries arrive only through the app's own update channel — the acceptance tests (airplane / cold-start) cover the pipeline, not the update channel.
          Example — the owner's case Movie sources + anime sources linked → AI proposes two feeds; manual mode can build the same with one content_type rule — both paths land in the same feeds.json.

          6.3 — Classify once, cache the label; pins are permanent v2.1

          The maintainer review named the cost correctly: classification inside the render path is a battery and latency tax on the exact screen users open most. So:

          • Classification is a job, not a render step. It runs once per work — on first sight of a new work_key, or in an explicit user-triggered batch — and writes to a local label cache: work_key → { label, confidence, model_version, timestamp }. Feed render and scroll read the cache; they never invoke the model.
          • Cache invalidation is boring too: labels recompute only when the user edits the rule set, upgrades the model and opts into re-classification, or requests it per entry. Model version is stored with the label so stale caches are detectable, not assumed.
          • Hysteresis guards re-classification (precise rule, v2.5): a label change always requires beating the old confidence by the margin (≥ +0.15); the ≥ 0.90 threshold alone only rescues the low-confidence band (< 0.60); failing candidates stay as visible alternates. Fuzzing showed why: threshold-only allowed A→B→A flip-flops between strong candidates. Both constants are named config — segments do not rotate when the model updates.
          • Labels GC (v2.2): rows unseen for labels_gc.days (default 90) are purged by the same batch job that classifies — never on cold start; cold start reads per key and never loads the table whole.
          • Cold-start determinism is an acceptance test — scoped to the rules layer (v2.4): a fresh install with an empty label cache and the same feeds.json + rules_pack must produce identical rules-layer segments to a warm device — golden files in CI run both paths. The AI layer is explicitly async: a cold start shows those entries in the «Sin asignar» pool until the classification batch lands, and arriving labels apply with a visible «segmentación actualizada» notice — the feed may enrich between launches, but never reshuffles silently.
          • Manual overrides are permanent and visible. A user pin ({ "pin": "Movies" }) sits above the classifier forever: pins survive re-classification, model upgrades, and restore from backup (they live in feeds.json), and show a small pin mark so the structure reads honestly. The answer to a mislabeled niche title is a one-tap pin — not a fight with the model. Pins are keyed by work_key hash, not row id (v2.2): a work that leaves and returns keeps its pin. Granularity: pin_segment (membership, default) or pin_position (membership + explicit order, opt-in per entry).
          • AI is a suggestion layer over hand-made structure, never a replacement. Rule-made feeds are the skeleton; AI proposals attach to it; pins and rules always win.

          6.4 — Two stores, one write path each v2.2

          Persistence is split so janitorial work can never touch intent — the cheapest insurance in the whole document:

          • LABELS — derived and disposable: k / label / conf / model_v / ts. Wiped whole without losing anything that matters; GC and model migrations touch only this store.
          • INTENT — durable user data, lives in feeds.json: feed definitions, rules, dedup policy, pins.
          • One write path each, never a shared transaction: a purge or a model migration is physically unable to reach intent. Backups always carry INTENT; LABELS ride along only as optional cache (recomputable).
